## 1. 构建过程

### 1. 构建过程概览

一个完整的**构建**（Build）过程包括：

```text
源文件1 (.cpp)  →  预处理  →  编译  →  汇编  →  目标文件1 (.o/.obj)
源文件2 (.cpp)  →  预处理  →  编译  →  汇编  →  目标文件2 (.o/.obj)
...
源文件n (.cpp)  →  预处理  →  编译  →  汇编  →  目标文件n (.o/.obj)

多个目标文件 (.o/.obj) + 库文件 (静态库 / 动态库)  →  链接  →  可执行文件 (.exe/a.out)
```

>[!TIP] **提示**：“编译”的狭义和广义
>**狭义的编译**指的是以上过程中的“编译”这一步。
>**广义的编译**一般指的是以上过程中的“预处理”、“编译”、“汇编”、“链接”中的某几步。
>
>广义的编译常见于口语。

### 1.2 预处理 Preprocessing

**预处理**是构建过程的第一步，它在**编译之前**对源代码进行文本级别的处理。预处理器不检查 C++ 语法，只处理以 `#` 开头的指令，**纯粹是文本替换和文件拼接**。

预处理器会处理以下指令（没学过的过目即可）：

| 指令类型       | 示例                        | 作用                         |
| ---------- | ------------------------- | -------------------------- |
| **头文件包含**  | `#include <iostream>`     | 将指定头文件的全部内容**复制粘贴**到当前位置   |
| **宏定义与替换** | `#define PI 3.14159`      | 将代码中所有的 `PI` 替换为 `3.14159` |
| **条件编译**   | `#ifdef DEBUG` / `#endif` | 根据条件决定保留或丢弃某段代码            |
| **特殊宏**    | `__LINE__`、`__FILE__`     | 提供当前行号、文件名等信息              |

例如，头文件展开：

```cpp
// test.cpp
#include "person.h"

int main() {
    Person p;
    return 0;
}
```

预处理后，`#include "person.h"` 会被 `person.h` 的**全部内容**替换：

```cpp
// 预处理后的 test.cpp（示意）
class Person {
    // ... person.h 的全部内容 ...
};

int main() {
    Person p;
    return 0;
}
```

**关键理解**：

1. 预处理后的代码仍然是**纯文本**，还没有变成机器码，也没有进行任何语法检查。
2. `#include` 的本质是**文件复制**——这就是为什么头文件守卫（`#pragma once` / `#ifndef`）能防止重复包含。
3. 预处理阶段**不检查函数是否真的存在**，只检查 `#include` 的文件路径是否存在、预处理指令的语法。

>[!TIP] **提示**：手动处理包含
>在学习本讲的 3, 4 章节时若有理解困难的地方，建议像以上代码块一样手动处理包含，即把头文件的内容粘贴到包含它的源文件的 `#include ...` 处，以帮助理解。

### 1.3 编译 Compilation

**编译**是构建过程中的核心阶段，它的任务是把预处理后的源代码（`.i` 文件）翻译成**汇编代码**（`.s` 或 `.asm` 文件）。

编译器在这个阶段会做以下几件事：

|步骤|做什么|检查什么|
|---|---|---|
|**词法分析**|把代码拆成一个个“单词”（Token）|检查是否有非法字符、数字是否合法|
|**语法分析**|检查这些单词的组合是否符合 C++ 语法规则|检查括号是否匹配、语句是否以分号结尾、函数声明是否正确|
|**语义分析**|检查语句是否有意义，类型是否正确|检查变量是否声明、类型是否匹配（如不能把 `string` 赋值给 `int`）|
|**生成汇编**|把通过检查的代码翻译成汇编指令|—|

**关键理解**：

1. 编译阶段**只检查当前文件**的语法和类型是否正确，不关心其他 `.cpp` 文件。
2. 如果 `main.cpp` 调用了 `Person::Print()`，编译器只检查这个调用**语法是否正确**（参数个数、类型等），不会去验证 `person.cpp` 中是否真的实现了它——那是链接阶段的工作（但是编译器会检查 `main.cpp` 中是否有 `Person::Print` 的声明）。

### 1.4 汇编 Assembly 

**汇编**是构建过程中的第三个阶段，它的任务是把**汇编代码**（`.s` 文件）翻译成**机器码**，生成**目标文件**（`.obj` 或 `.o`）。

汇编器在这个阶段会做以下几件事：

| 步骤          | 做什么                                                        |
| ----------- | ---------------------------------------------------------- |
| **指令翻译**    | 把每条汇编指令翻译成对应的 CPU 机器码                                      |
| **生成符号表**   | 记录当前文件中所有**已定义**的符号（函数名、全局变量名）及其在文件中的位置（偏移量）               |
| **标记未定义符号** | 对于引用了但**未在当前文件中定义**的符号（如外部函数），标记为“未解析”（undefined），留待链接阶段处理 |

**目标文件的内容**：

|组成部分|说明|
|---|---|
|**机器指令**|CPU 能直接执行的二进制代码|
|**符号表**|记录已定义符号的位置 + 未解析符号的“待填名单”|

例如：

```text
main.obj（目标文件结构简化版）
┌────────────────────────────────┐
│ 机器指令区                       │
│   main   函数的机器码            │
│   Helper 函数的机器码            │  ← 当前文件定义的辅助函数
├────────────────────────────────┤
│ 符号表                          │
│   Helper:        0x0010        │  ← 已定义（当前文件提供）
│   main:          0x0000        │  ← 已定义（当前文件提供）
│   Person::Print: 未解析 (U)     │  ← 未定义，需要链接时在其他.obj中找
│   std::cout:     未解析 (U)     │  ← 未定义，需要链接时在库文件中找
└────────────────────────────────┘
```

>[!TIP] **提示**：关于“符号表”
>若对“符号表”的概念不熟悉，请回顾 [[12. 引用、const 限定符#^SymbolTable|12-1.3.1 符号表]] 。

**关键理解**：

1. **汇编阶段不检查语法**：语法已经在编译阶段检查过了，汇编器只是**机械地翻译**，不再做语法或类型检查。
2. **符号表是链接的“通讯录”**：
    - **已定义符号**：当前文件自己提供的“服务”（如 `main` 函数）
    - **未解析符号**：当前文件需要的“服务”（如 `Person::Print`），但不知道对方在哪里
3. **每个 `.cpp` 文件生成一个独立的 `.obj` 文件**：

```
text

main.cpp   →  预处理  →  编译  →  汇编  →  main.obj
person.cpp →  预处理  →  编译  →  汇编  →  person.obj
utils.cpp  →  预处理  →  编译  →  汇编  →  utils.obj
```

4. **目标文件还不是可执行程序**：它只是一堆“零件”，还没有“组装”起来。外部函数的地址还空着，需要链接阶段来填充。

### 1.5 链接 Linking

**链接**是构建过程中的最后一个阶段。它的任务是把**多个目标文件**（`.obj` / `.o`）和**库文件**（`.lib` / `.a`）**合并**成一个**完整的可执行文件**（`.exe` / `a.out`），并解决所有“未解析”的符号引用。

**简单来说**：编译和汇编把每个 `.cpp` 文件变成了一个“零件包”，链接器的工作就是把这些零件**组装**成一个能运行的完整程序。

链接器在这个阶段会做以下几件事：

|步骤|做什么|
|---|---|
|**合并段**|把所有目标文件的代码段（`.text`）、数据段（`.data`）等合并到一起|
|**解析符号**|查找每个“未解析符号”在哪个目标文件中被定义了，把它的地址填进去|
|**重定位**|调整所有指令中的地址引用，让它们指向最终合并后的正确位置|
|**库文件处理**|从静态库中提取需要的目标文件，也参与合并（静态链接）|
|**生成可执行文件**|输出一个完整的、可加载到内存中运行的程序文件|

以符号解析为例：

假设我们有两个目标文件：

```text
main.obj 的符号表：
┌─────────────────────────────┐
│ main:         已定义 0x0000  │
│ Person::Print: 未解析  (?)   │
└─────────────────────────────┘

person.obj 的符号表：
┌─────────────────────────────┐
│ Person::Print: 已定义 0x0020 │
│ Person::Person: 已定义 0x0000│
└─────────────────────────────┘
```

链接时，链接器会进行符号解析：

```text
main.obj 中的 "Person::Print (?)" 
   ↓
查找所有目标文件中的符号表
   ↓
在 person.obj 中找到 "Person::Print: 已定义 0x0020"
   ↓
把 main.obj 中的占位符替换为 person.obj 中函数的实际地址
```

链接有两种方式：

| 链接方式                     | 说明                             | 特点                    |
| ------------------------ | ------------------------------ | --------------------- |
| **静态链接** Static Linking  | 在构建时把库代码**复制**到可执行文件中          | 可执行文件大，独立运行，更新库需要重新链接 |
| **动态链接** Dynamic Linking | 在**运行时**才加载库（如 `.dll` / `.so`） | 可执行文件小，多个程序共享同一份库代码   |

关键理解：

1. **链接阶段才真正“检查函数是否存在”**：  
    如果 `main.cpp` 调用了 `Person::Print()`，但 `person.cpp` 中没有实现它，编译阶段**不会报错**（因为编译只检查语法），但在**链接阶段**就会报“未解析的外部符号”错误。
2. **每个 `.obj` 都是独立的“零件包”**：  
    链接器像一个拼图师，把多个零件拼成一个完整的可执行文件。
3. **库文件是提前打包好的目标文件集合**：  
    标准库（`iostream`、`vector` 等）已经预编译成了库文件（`.lib` / `.a`），链接时直接使用，不需要我们手动编译。
4. **链接器只解析被引用的符号**：  
    如果某个目标文件中的函数从未被其他地方调用，链接器可能会丢弃它（这在优化构建中很常见，可减小可执行文件体积）。


>[!QUESTION] **问题**：为什么 VS 有时需要“清理并重新生成解决方案”？
>在 VS 中，当你按下 `F5` 或点击“生成解决方案”时，实际上是在执行 **预处理 → 编译 → 汇编 → 链接** 的完整流程。
>
>有时候 VS 会莫名其妙报错，这个时候我们会重启 VS 并先后点击顶部菜单栏的“生成-清理解决方案”和“生成-重新生成解决方案”以尝试解决问题。
>
>原因：
>
>VS 默认使用**增量编译**（Incremental Build），只重新编译修改过的文件以节省时间。但增量编译的依赖检测并不完美，当以下情况发生时，旧的中间文件（`.obj`、`.pdb`）可能过时：
>
>- 修改了头文件，但依赖它的 `.cpp` 没有被重新编译
>- 修改了项目配置（如宏定义、编译选项）
>- 切换了 Git 分支
>- 升级了 VS 或 SDK

## 2. 链接属性 Linkage

### 2.1 链接属性的基本概念

**链接属性**决定了一个**实体**（Entity）（如变量、函数、类等）在**多个目标文件之间是否可见**，以及在链接时能否被其他文件访问。

简单来说：**链接属性控制着一个实体的“可见范围”**——它是只在这个文件内生效，还是整个程序都能用？

| 链接属性     | 英文               | 可见范围         | 能否跨文件访问 |
| -------- | ---------------- | ------------ | :-----: |
| **无链接**  | No Linkage       | 仅在当前作用域内可见   |  ❌ 不能   |
| **内部链接** | Internal Linkage | 仅在当前文件内可见    |  ❌ 不能   |
| **外部链接** | External Linkage | 整个程序的所有文件都可见 |   ✅ 能   |

>[!NOTE] 概念：实体（Entity）
>
>在 C++ 中，**实体（Entity）** 是指**可以在编译器和链接器层面被识别和引用的程序元素**。
>
>简单来说，**凡是在代码中有“身份”的东西，都可以称为实体**。
>
>常见的实体包括：
>
>|实体类型|示例|说明|
>|---|---|---|
>|**变量**|`int count;`|每个变量都是一个实体|
>|**函数**|`void Print();`|每个函数都是一个实体|
>|**类型**|`class Person {};`|类、结构体、枚举都是实体|
>|**静态成员**|`Person::s_count`|类的静态成员也是实体|
>|**模板特化**|`std::vector<int>`|模板实例化后的类型也是实体|
>|**枚举值**|`enum Color { kRed };` 中的 `kRed`|枚举值也是实体|
>
>**与“名字”的区别**：
>
>- **名字**：是我们在代码中写的标识符（如 `count`），是程序员用来指代实体的“代号”。
>    
>- **实体**：是编译器赋予某个程序元素的“身份”，对应一个具体的**内存地址**或**类型定义**。
>    
>```cpp
>int count = 10;   // "count" 是一个名字，它代表的变量是 一个实体
>```
>
>**==（重要）==** **链接属性描述的就是“实体”能否跨文件被访问**，而不是“名字”本身能否跨文件出现。同一个名字在不同文件里可能代表不同的实体（如 `static` 变量），这正是链接属性发挥作用的地方。

三种链接属性的对比：

| 特性              | 无链接       | 内部链接                     | 外部链接                        |
| --------------- | --------- | ------------------------ | --------------------------- |
| **可见范围**        | 仅当前作用域    | 仅当前文件                    | 整个程序                        |
| **能否跨文件访问**     | ❌ 不能      | ❌ 不能                     | ✅ 能                         |
| **不同文件同名会冲突吗？** | —         | ❌ 不会                     | ✅ 会（重复定义错误）                 |
| **是否写入符号表**     | ❌ 不写入     | ✅ 写入（局部符号）               | ✅ 写入（全局符号）                  |
| **典型例子**        | 局部变量、函数参数 | `static` 变量、`const` 全局变量 | 普通全局变量、普通函数                 |
| **头文件中的使用建议**   | —         | ✅ 适合放 `constexpr` 常量     | ⚠️ 需要配合 `extern` 或 `inline` |

>[!TIP] 提示：关于“文件”
>接下来所说的“文件”指的都是目标文件（.obj），不要当成源文件或头文件。

### 2.2 无链接  No Linkage

**无链接**的实体只在当前作用域内有效，不能在其他作用域或文件中被引用。

这类实体**不参与链接过程**——链接器根本不会看到它们，例如：

```cpp
void Func() {
    int local_var = 10;   // ❌ 无链接（局部变量）
    // 只能在 Func 内部使用，其他函数无法访问
}
```

**常见的无链接实体**：

| 实体类型             | 示例                       | 说明            |
| ---------------- | ------------------------ | ------------- |
| **局部变量**         | `void Func() { int x; }` | 只在函数内部可见      |
| **函数参数**         | `void Func(int x)`       | 只在函数内部可见      |
| **局部类/枚举**       | `struct LocalStruct {};` | 只在当前作用域内可用    |
| **`const` 局部变量** | `const int x = 10;`      | 和其他局部变量一样，无链接 |

无链接的实体**不会被写入目标文件的符号表**，因此链接器完全不知道它们的存在。

### 2.3 内部链接 Internal Linkage

**内部链接**的实体**只在当前文件内可见**。不同的文件可以各自定义同名的内部链接实体，互不干扰。

**内部链接的实体不会被其他文件看到，也不会与其他文件中的同名符号发生冲突，例如：

```cpp
// file1.cpp
static int g_count = 100;      // ✅ 内部链接
static void Helper() {}        // ✅ 内部链接

// file2.cpp
static int g_count = 200;      // ✅ 完全独立，不冲突
static void Helper() {}        // ✅ 完全独立
```

**获得内部链接的常见方式**：

| 方式                             | 示例                         | 说明            |
| ------------------------------ | -------------------------- | ------------- |
| **`static` 关键字（全局作用域）**        | `static int count;`        | 最经典的方式        |
| **`const` / `constexpr` 全局常量** | `const int PI = 3.14;`     | 默认内部链接        |
| **无名命名空间**                     | `namespace { int count; }` | C++ 中更推荐的现代方式 |

关于 `const` 全局变量默认内部链接这一点，需要注意：它们与 `static` 的效果相同，但机制不同——`static` 是显式指定链接属性，`const` 是语言规则默认的行为。

关于 `static` 说明符和命名空间我们将在下一讲的 [[17. static 说明符、命名空间、枚举#1. static 说明符|17-1. static 说明符]] 和 [[17. static 说明符、命名空间、枚举#2. 命名空间|17-2. 命名空间]] 学到。

### 2.4 外部链接 External Linkage

**外部链接**的实体**可以被整个程序的所有文件访问**。这是跨文件共享变量和函数的默认方式。

例如：

```cpp
// file1.cpp
int g_count = 100;           // ✅ 外部链接（默认）
void Print() { /* ... */ }   // ✅ 外部链接（默认）

// file2.cpp
extern int g_count;          // ✅ 声明外部的 g_count
extern void Print();         // ✅ 声明外部的 Print

int main() {
    std::cout << g_count;    // 访问 file1.cpp 中的 g_count
    Print();                 // 调用 file1.cpp 中的 Print
}
```

>[!TIP] **提示**：`extern` 的作用
>`extern` 说明符在以上代码中的作用是标记某个实体的定义在其它文件，让编译器找不到定义时先别报错。

**获得外部链接的常见方式**：

| 方式                        | 示例                                   | 说明            |
| ------------------------- | ------------------------------------ | ------------- |
| **普通全局变量/函数**             | `int count;` `void Func();`          | 默认外部链接        |
| **`extern` 声明**           | `extern int count;`                  | 声明但不定义        |
| **`inline` 变量/函数（C++17）** | `inline int count = 10;`             | 允许多处定义，链接器会合并 |
| **模板**                    | `template<typename T> class Vec {};` | 模板有外部链接       |

>[!WARNING] **注意**：外部链接和声明
>外部链接的实体 `e` 虽然在其他文件可见，但如果其他文件 `F` 要访问这个实体 `e`，则 `F` 必须要（至少选择以下一种）：
>
>- 声明这个实体 `e`
>- 包含这个实体 `e` 的声明
>  
>因为链接之前的编译阶段要求文件 `F` 中访问实体 `e` 前必须有 `e` 的声明，而且链接器只是链接不同符号对应的内存地址，不干涉编译器检查声明的工作。

关于如何用 `inline` 和 `extern` 声明 / 定义外部链接的变量我们将在本讲的 [[16. 构建过程、链接属性、extern、inline#3. extern 说明符|3. extern 说明符]] 和 [[16. 构建过程、链接属性、extern、inline#4. inline 说明符|4. inline 说明符]] 学到。

### 2.5 头文件中的链接属性

理解链接属性后，我们就能明白为什么头文件中有特定的写法：

| 头文件中的写法                        | 链接属性     | 是否正确      | 原因                    |
| ------------------------------ | -------- | --------- | --------------------- |
| `constexpr int kSize = 10;`    | 内部链接     | ✅ 正确      | 每个 `.cpp` 有一份独立副本，不冲突 |
| `inline int count = 0;`（C++17） | 外部链接（特殊） | ✅ 正确      | 链接器合并多份定义             |
| `extern int count;`            | 外部链接（声明） | ✅ 正确      | 只声明不定义，告诉编译器“定义在别处”   |
| `int count = 0;`               | 外部链接（定义） | ❌ **错误！** | 多个 `.cpp` 包含后重复定义     |

## 3. extern 说明符

### 3.1 extern 说明符的基本概念

`extern` 是一个**存储类说明符（Storage Class Specifier）**，它的核心作用是：**告诉编译器“这个名字所代表的实体，定义在其他地方”**。

简单来说：`extern` 是一个“**声明**”关键字，而不是“**定义**”关键字。它告诉编译器“有这个实体存在，但请不要在这里分配内存，它的内存分配在别处。”

```cpp
// config.h
extern int g_count;   // 声明：告诉编译器“有 g_count 这个变量，但在别处”

// config.cpp
int g_count = 0;      // 定义：在这里分配内存
```

### 3.2 声明与定义分离

`extern` 最重要的用途是**在头文件中声明全局变量，在源文件中定义它们**，从而实现跨文件共享。

```cpp
// ===== global.h =====
#pragma once
extern int g_app_version;      // 声明（不分配内存）（app 版本）
extern void PrintVersion();    // 函数默认就是 extern，写不写都一样

// ===== global.cpp =====
#include "global.h"
int g_app_version = 3;         // 定义（分配内存）
void PrintVersion() {          // 定义
    std::cout << g_app_version;
}

// ===== config.cpp ===== （配置文件）
extern int g_app_version;      // 这里仅作演示，实际推荐包含头文件而非用 extern
void Adapt(int version) {      // 根据版本自适应配置
	// 自适应逻辑
}

// ===== main.cpp =====
#include "global.h"
int main() {
	Adapt(g_app_version);      // ✅ 使用
    g_app_version = 4;         // ✅ 使用
    PrintVersion();            // ✅ 使用
    return 0;
}
```

以上代码中需要注意的地方：

- 对于要文件间共享的（非常量）变量（即外部链接的实体）：

1. 这个变量在其所属的源文件中直接定义，在其所属的头文件中用 `extern` 声明。
2. 其他文件若要使用该变量，要么包含其所属头文件，要么用 `extern` 声明它（推荐前者）。

- 对于要文件间共享的全局函数（即外部链接的实体）：

1. 全局函数默认是外部链接的实体，不需要在其所属头文件中额外用 `extern` 说明。
2. 其他文件若要调用该函数，要么包含其所属头文件，要么用 `extern` 声明它（推荐前者）。

>[!WARNING] 注意：`extern` 和 包含头文件的“坑”
>对于一个外部链接的实体，如果一个文件用 `extern` 声明了它且同时包含了它所属的头文件：
>
>1. 若该文件的 `extern` 声明和其所属头文件中的声明匹配则正常编译。
>2. 否则编译器（更准确地说是链接器）可能在链接时报错，或更糟——产生==未定义行为==。
>   
>例如：
>```cpp
>// ===== global.h =====
>#pragma once
>extern int g_version;      // 声明：int 类型
>
>// ===== config.cpp =====
>#include "global.h"        // 包含了正确的声明
>
>extern float g_version;    // ❌ 手写了一个不一致的声明！
>
>void PrintVersion() {
>    std::cout << g_version;   // 此时编译器会用 float 规则去解释这块内存
>}
>```
>
>以上代码中，`extern float g_version;` 与 `int` 类型不一致，使用 `float` 规则解释 `int` 内存，导致 **UB** 。
>
>**因此**：建议不要同时使用 `#include` 和手写 `extern`。优先选择“只通过头文件包含来获得声明”，这样可以确保所有声明完全一致，避免这类问题。

### 3.3 extern 与 const

`const` 全局常量在 C++ 中默认是**内部链接**的（只在当前文件可见）。如果需要跨文件共享 `const` 常量，必须用 `extern` 强制改变其链接属性。

```cpp
// ===== config.h =====
#pragma once
extern const int kMaxSize;     // 声明（强制外部链接）

// ===== config.cpp =====
#include "config.h"
const int kMaxSize = 100;      // 定义（分配内存）
```

**为什么需要这样写？**

| 写法                                                                      | 链接属性 | 结果                        |
| ----------------------------------------------------------------------- | ---- | ------------------------- |
| `const int kMaxSize = 100;`（头文件）                                        | 内部链接 | 每个 `.cpp` 有一份独立副本，无法跨文件共享 |
| `extern const int kMaxSize;`（头文件） + `const int kMaxSize = 100;`（`.cpp`） | 外部链接 | 所有文件共享同一份 `MAX_SIZE`      |

>[!TIP] 提示：`constexpr` 常量
>`constexpr` 常量默认内部链接，它一般直接在头文件中定义，而非在源文件定义，所以不需要再用 `extern` 声明。其他文件要用该 `constexpr` 常量的话直接包含其所属头文件即可：
>
>```cpp
>// config.h
>constexpr int kMaxSize = 100;          // ✅ 内部链接，每个文件可以包含此定义
>extern constexpr int MAX_SIZE = 100;   // ❌ 编译错误！
>```
>
>注意：不要用 `extern` 说明 `constexpr` 常量。
>
>另外，C++17起，`constexpr` 变量**隐式 `inline`**，因此可直接在头文件中定义并跨文件共享。

### 3.4 extern "C" 链接规范

`extern "C"` 是一个**链接规范**（Linkage Specification）**，它告诉 C++ 编译器：“这段代码按 C 语言的规则处理，不要进行 C++ 的名称修饰。”

**为什么需要它？**

C++ 支持函数重载，编译器会对函数名进行**名称修饰（Name Mangling）**。例如：

| 函数声明                  | C++ 编译器修饰后的名字（示例） | C 编译器修饰后的名字 |
| --------------------- | ----------------- | ----------- |
| `void Func(int x)`    | `_Z4Funci`        | `_Func`     |
| `void Func(double x)` | `_Z4Funcd`        | （不允许同名）     |

如果 C++ 程序要调用一个 C 语言编写的库，链接时会去找修饰后的名字（如 `_Z4Funci`），但 C 库中只有未修饰的名字（如 `_Func`），导致链接失败。`extern "C"` 告诉 C++ 编译器“不要修饰这个名字”，从而正确链接。

```cpp
// 假设这是一个 C 语言库的头文件 c_lib.h
// c_lib.h
void c_function(int x);   // C 编译器会生成 _c_function

// 在 C++ 中使用时
extern "C" {
    #include "c_lib.h"    // 告诉 C++ 编译器：按 C 规则处理这个头文件中的所有声明
}

int main() {
    c_function(10);       // ✅ 链接成功（找 _c_function，而不是 _Z10c_functioni）
    return 0;
}
```

**`extern "C"` 的常见用途**：

| 场景                   | 说明                                                                    |
| -------------------- | --------------------------------------------------------------------- |
| **调用 C 标准库**         | 如 `<stdio.h>`、`<math.h>`（现代 C++ 头文件如 `<cstdio>` 内部已经包含了 `extern "C"`） |
| **调用第三方 C 库**        | 如某些硬件驱动、操作系统 API                                                      |
| **在 C++ 中实现 C 兼容接口** | 让 C 程序也能调用你的 C++ 函数                                                   |

```cpp
// 让 C 程序也能调用这个 C++ 函数
extern "C" void MyFunction() {
    // 实现
}
```

## 4. inline 说明符

### 4.1 inline 说明符的基本概念

`inline` 是一种**函数说明符** / **声明说明符**（Function Specifier / Declaration Specifier），也是 C++ 中一个“双重身份”的关键字：

| 身份        | 作用                       | 关注者     |
| --------- | ------------------------ | ------- |
| **链接属性**  | 允许多个文件中定义同一个实体，链接器会合并    | **链接器** |
| **编译器优化** | 建议编译器将函数体展开到调用处，避免函数调用开销 | **编译器** |

**现代 C++ 中，`inline` 的“链接属性”身份比“优化”身份更重要。**

### 4.2 inline 变量

`inline` 告诉链接器：**“这个实体允许在多个文件中被定义，你只需要保留一份即可。”**

```cpp
// config.h
#pragma once
inline int g_count = 0;   // 多个 .cpp 包含，链接器合并为一份
```

**为什么需要这个能力？**

在 C++17 之前，如果要在多个 `.cpp` 文件间共享一个全局变量，你必须在头文件中用 `extern` 声明，再单独在一个 `.cpp` 文件中定义。这很麻烦——你需要维护两个地方。

`inline` 变量（C++17 起）解决了这个问题：**你可以在头文件中直接定义全局变量，而不需要额外的 `.cpp` 文件。**

>[!EXAMPLE] `extern` 与 `inline` 的对比示例
>1. 使用 `extern`：（传统 C++ 方式）
>
>```cpp
>// ===== config.h =====
>#pragma once
>extern int g_app_version;    // 声明：告诉编译器“这个变量在别处”，不要再分配内存
>
>// ===== config.cpp =====
>#include "config.h"
>int g_app_version = 3;       // 定义：唯一的一份，分配内存
>
>// ===== main.cpp =====
>#include "config.h"
>int main() {
>    g_app_version = 4;       // 使用
>    return 0;
>}
>```
>
>**特点**：需要维护两个文件（`.h` + `.cpp`）。`extern` 只在头文件中声明，定义必须在唯一的 `.cpp` 文件中。
>
>2. 使用 `inline`：（C++17 现代方式）
>
>```cpp
>// ===== config.h =====
>#pragma once
>inline int g_app_version = 3;    // 定义：直接写在头文件中，分配一个内存 a ，并写入3
>
>// ===== main.cpp =====
>#include "config.h"
>int main() {
>    g_app_version = 4;           // 使用，在内存 a 写入 4
>    return 0;
>}
>
>// ===== other.cpp =====
>#include "config.h"
>void OtherFunc() {
>    g_app_version = 5;           // 也使用，和 main.cpp 共享同一个变量，在内存 a 写入 4
>}
>```
>
>**特点**：只需要维护一个头文件。链接器发现 `g_app_version` 在多个 `.cpp` 中都有定义，会自动合并为一份，不会报重复定义错误。
>
>|对比维度|`extern` 方式|`inline` 方式（C++17）|
|---|---|---|
|**需要额外的 `.cpp` 文件**|✅ 必须|❌ 不需要|
|**头文件中的写法**|`extern int g_app_version;`|`inline int g_app_version = 3;`|
|**定义位置**|唯一的 `.cpp` 中|直接在头文件中|
|**链接器行为**|只有一个 `.obj` 中有定义|多个 `.obj` 中有定义，链接器合并|
|**适用 C++ 版本**|所有版本|C++17 起|
|**推荐程度**|传统方式|**更推荐（简洁）**|

>[!QUESTION] **问题**：如果头文件和源文件都定义了同一个（`inline`）变量会怎么样？
>如果 `main.cpp` 包含了 `config.h`，且两个文件都写了变量 `a` 的定义：
>
>|头文件 (`config.h`)|源文件 (`main.cpp`) 中的写法|结果|错误类型|
|---|---|---|---|
|`inline int a = 0;`|`int a = 0;`|❌ 链接错误|重复定义（ODR违规）|
|`inline int a = 0;`|`inline int a = 0;`|✅ 正常|共享变量（ODR违规）|
|`inline int a = 0;`|`inline int a = 1;`|⚠️ **未定义行为**|链接器随机选一个值|
|`inline int a = 0;`|`int a = 1;`|❌ 链接错误|重复定义（ODR违规）|
>
>但对于 VS 的 MSVC 编译器，以上四种都属于“重定义”错误，会明确报错。这也反映了编译器的实现可能比 C++ 标准更严格。

### 4.3 inline 函数

`inline` 函数也叫**内联函数（Inline Function）**，它在头文件中定义时，也允许多处定义——这是 `inline` 最初的设计用途。

也就是说，在头文件定义全局函数时，必须要用 `inline` 说明该函数。但对于头文件中的成员函数，定义时默认为 `inline` 函数，所以不需要再用 `inline` 说明成员函数。

```cpp
// ===== utils.h =====
#pragma once
inline int Square(int x) { // 平方计算
    return x * x;
}

// ===== main.cpp =====
#include "utils.h"
int a = Square(5);   // 25

// ===== other.cpp =====
#include "utils.h"
int b = Square(6);   // 36
// 链接器会合并 Square 的定义，只保留一份
```

>[!QUESTION] **问题**：为什么类（class/struct）可以在头文件中定义？
>全局变量在头文件中定义会报“重复定义”错误，为什么类（或枚举）在头文件中定义就没问题？
>
>**关键区别**：类定义是给编译器看的“**图纸**”，而不是需要内存的“**实物**”。
>
>- **普通变量/函数** 是“实物”——在程序中占用内存，每个 `.cpp` 文件如果各自定义一份，链接时就会冲突。
>- **类定义** 是“图纸”——它只是告诉编译器“这个类型的对象长什么样”，并不产生实际的机器码。多个 `.cpp` 文件各自读到同一份“图纸”，只要一模一样，就是安全的。
>
>这也是为什么类的成员函数如果在类体内实现，默认是 `inline` 的——因为这些函数也像“图纸的一部分”一样，需要在每个包含头文件的 `.cpp` 中都可见，且不能产生重复定义。

编译器会选择性地对**内联函数**进行**内联展开（Inlining / Inline Expansion）**（函数体展开），例如：

```cpp
inline int Square(int x) {
    return x * x;
}

int main() {
    int a = 5;
    int result = Square(a);   // 调用 Square
    return result;
}
```

编译器内联展开的效果：

```cpp
int main() {
    int a = 5;
    int result = a * a;   // 函数调用被替换为函数体
    return result;
}
```

`inline` 只是对编译器的一个“建议”，编译器会根据优化级别、函数大小等因素，决定是否真正执行内联展开。现代编译器在开启优化后，会自动决定哪些函数适合内联，因此 `inline` 关键字作为建议优化的作用已经逐渐弱化。

>[!QUESTION] **问题**：哪些函数适合作为 `inline` 函数？（哪些函数适合在头文件定义？）
>**`inline` 函数的本质是用“代码膨胀”换取“性能提升”。** 它最适合那些**短小、频繁调用、且对性能敏感**的函数。
>
>1. 适合作为 `inline` 函数：
>
>|类别|示例|理由|
|---|---|---|
|**Getter / Setter**|`int GetAge() const { return age_; }`|极其短小（一行），调用极其频繁，展开后几乎没有代码膨胀|
|**简单的数学运算**|`int Square(int x) { return x * x; }`|逻辑简单，展开后比函数调用更快|
|**比较运算符**|`bool IsPositive(int x) { return x > 0; }`|简单且频繁使用|
|**模板函数**|`template<typename T> T Max(T a, T b)`|模板默认就是 `inline` 语义，编译器会自动处理|
|**类内部定义的成员函数**|类内实现的成员函数默认就是 `inline`，不需要额外写关键字|比如 `Person::GetName()`，如果直接在类中实现，已经是 `inline` 了|
|**转换函数（类型转换运算符）**|`operator bool() const { return ptr_ != nullptr; }`|通常很短，且被频繁调用|
>
>2. 不适合作为 `inline` 函数：
>   
>|类别|示例|理由|
|---|---|---|
|**大型函数（超过 5-10 行）**|复杂的业务逻辑或算法函数|展开后代码膨胀严重，反而降低缓存命中率|
|**包含循环的函数**|`for`、`while` 循环|循环体已经在占用 CPU 时间，展开的收益极小|
|**递归函数**|`int Factorial(int n) { return n * Factorial(n-1); }`|递归无法展开，即使展开也会导致无限膨胀|
|**虚函数（`virtual`）**|`virtual void Print() const;`|虚函数的调用依赖运行时多态，通常不能展开|
|**只在单个 `.cpp` 中使用的函数**|只在一个文件中用到的辅助函数|没有必要暴露给其他文件，应该用 `static` 限制作用域|
|**不稳定的函数（频繁修改）**|经常修改逻辑的函数|修改头文件会触发大量重新编译，增加构建时间|

>[!NOTE] 概念：**One Definition Rule（ODR）（单一定义规则）**
>我们之前学的 `extern` 和 `inline` 其实都是为了保障 ODR。
>
>ODR（One Definition Rule，单一定义规则）是 C++ 中最基础也最重要的规则之一，它规定：
>
>1. **在整个程序中，任何普通实体（变量、函数、枚举）只能有一个定义。**
>2. **对于允许多个定义的实体（类、模板），它们的定义必须完全相同。**
>
>违反 ODR 会导致**链接错误（重复定义）**，或更糟——**未定义行为**（类型不一致时）。
>
>#### 例外（允许重复定义的情况）
>
>| 实体类型 | 允许重复定义的原因 | 链接器行为 |
>| :--- | :--- | :--- |
>| **`inline` 函数/变量** | 明确告诉链接器“可以重复” | 合并为一份 |
>| **模板（函数/类）** | 必须在每个使用它的 `.cpp` 中实例化 | 只保留一份实例化 |
>| **类定义** | 必须在头文件中，以便被多个 `.cpp` 共享 | 编译器检查一致性，否则未定义行为 |
>
>**常见 ODR 违规**
>
>```cpp
>// ❌ 错误：在头文件中定义普通全局变量
>// test.h
>int g_count = 0;   // 被多个 .cpp 包含 → 重复定义
>
>// ❌ 错误：在头文件中定义普通函数
>// utils.h
>int Add(int a, int b) { return a + b; }   // 被多个 .cpp 包含 → 重复定义
>```
>
>**解决方案**：
>
>```cpp
>// ✅ 用 inline
>inline int g_count = 0;                 // C++17
>inline int Add(int a, int b) { return a + b; }
>
>// ✅ 或用 extern（声明）+ 在 .cpp 中定义
>extern int g_count;   // 头文件中声明
>int g_count = 0;      // .cpp 中定义
>```
